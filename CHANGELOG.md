- `scripts/check-drift.sh` compares what runs with the repository, not only the files on disk. It reads the files of the Strata tree and of the service's checkout and hashes them as git stores them, instead of asking `git status`. So a file that `git status` hides is compared too, and a text file (git's `text` attribute) differs only if more than its CRLF line ends differ. The attributes are the commit's own: not those of the working tree, of the user or of the system, and a repository's `info/attributes` that sets one is drift. It writes nothing in the repositories. It checks, also while the service is stopped, that the service manager gives every service no variable but `LANG`, `LANGUAGE`, `LC_*` and `PATH`, and a `PATH` of directories that only root can change (no `systemctl set-environment`, no `DefaultEnvironment=`). It compares each drop-in in `systemd/<unit>.d/` with its installed copy, as it does the units, and finds any other `.conf` in that directory. It also checks that systemd has loaded the drop-ins, and that the memory limits they set are in the unit's cgroup (`memory.max`, `memory.swap.max`) while it runs. For `user-1003.slice`, which has no unit file in the repository, the system's own unit file and drop-ins under `/usr/lib/systemd/system` (`user-.slice.d/10-defaults.conf`) are allowed, and a copy of the repository's values that `systemctl set-property --runtime` wrote is noted. It reads every drop-in directory that systemd reads for a unit (`<unit>.d`, its dash prefixes such as `user-.slice.d`, and `<type>.d`, in every unit search directory, in systemd's order), and skips a name that starts with "." (an editor's lock file), as systemd does: a `.conf` there that systemd has not loaded is drift ("run daemon-reload"), and so is a runtime drop-in that sets nothing or links to `/dev/null`, which masks a drop-in of its name. While `strata-q3` is active, it checks that:
  - server.py's process is what its unit says: the command line, the program (and that it was not replaced on disk since), the working directory, the user and group, `LimitMEMLOCK`, `LimitNOFILE`, `OOMScoreAdjust` and `NoNewPrivileges`, and the file system that its `ProtectSystem=`, `PrivateTmp=` and `ProtectHome=` give (from its `mountinfo`); its environment is that of its loaded unit, with nothing else but what systemd sets, and `HOME`, `USER`, `LOGNAME` and `SHELL` as systemd sets them from the user's passwd entry ("restart pending" otherwise);
  - server.py runs one engine (none only when the model is unloaded on purpose), and no other engine runs;
  - the engine is the listed binary, with the command line, the working directory and the environment that server.py makes of the live config, also the `LC_CTYPE` that Python sets in the C locale (PEP 538). A config value of the wrong shape (`env` not a mapping, `lib_dirs` or `args` not a list of strings) is drift, not a traceback. A config setting whose effect the check does not follow is drift, and the engine is then compared by hand: `vision`, `replicas`, `effort_position` `end`, a learned expert profile, a backend other than CUDA, or a card order that server.py would measure. On the machine, `tests/test_check_drift.py` compares this model with server.py's own functions;
  - the engine maps the listed CUDA libraries and no other copy of them, and no file outside the system's directories that the list does not name or that was replaced after the start (a library from `~/cuda-12.9/bin`, first on its library path, too). It looks each mapped library up as glibc's loader would at the next start: by its SONAME, in each directory of the library path, and there first in the subdirectories that this CPU's loader searches (`glibc-hwcaps/x86-64-v3` to `x86_64`, as `LD_DEBUG=libs` lists them), the library's own directory included. A file of that name that the loader would find first is drift, and so is a mapped library that is not a readable ELF file;
  - the server has no shared settings (`GET /settings`). The config's key is sent only to `127.0.0.1`, `::1` or `localhost`, not through a proxy or a redirect, not when it holds a control character, and only when every socket that listens on the server's port is server.py's or a child's, as the check finds them again right before each request; a listener of another process, or none, is drift. Of a failed request the check prints the HTTP status or the error's type, never the error's text, which can hold the key.

  A file that the service read at its start (the live config, a listed file but a record of how the pack and the venv were made, the Strata tree's server code, the venv's files) or its installed unit that changed after the start is drift ("restart pending"): its modification time, or its inode alone, when a link, its mode or its owner changed, or a content was put back with its old modification time (`cp -p`), and the service runs what it read before. Only a file that the engine maps, the very file (its device and inode), whose inode alone changed and whose content is the list's, is a note; over 1 GiB the note says to run `--full`, which hashes it. So removing the IQ3_XXS name of the shard that IQ3_S shares by a hard link, which the engine maps, gives that note. An entry added, removed or renamed after the start where server.py imports from, or in the venv, is a note that names the directory and, of its entries, up to four that are newer than the start, for up to eight such directories (a removed entry is gone, so it cannot be named); a module added there is drift, as any module is that neither the commit nor the list has. The start is the earlier of the main process's start by the boot clock and systemd's record of it, so neither a suspend nor a step of the clock hides a change. A start script of the service's checkout that changed, or a directory of the engine's library path, is noted. The check verifies the venv without running anything from it: its python is the system's, and every file in it is one that `python -m venv` makes, one a package's `RECORD` gives (as it gives it, by a sha256 or stronger hash) or one the list names. `config/strata-venv.txt` pins each package's `RECORD` by its sha256, so a file changed together with its row in the `RECORD`, a row without a hash and a second `dist-info` directory of a package all show. A `.pth` in `lib/python3.10/dist-packages`, which Debian's python reads too, a `bin/pyvenv.cfg`, which wins over the venv's own, and a `.pth`, `usercustomize` or `sitecustomize` in the service user's `~/.local/lib/python*/site-packages` are drift. Where server.py imports from, a module that the pinned commit does not have and the list does not name (`json.py`, `json.pyc`, an extension module, a package, or a directory with no file of the commit, which Python imports as a namespace package; only names that an import can reach) is drift, and so is cached bytecode that Python would run instead of its source when it is not what that source compiles to. Its own Python runs without `site`, and a venv's `python3` on `PATH` is drift. A file that the check would read and that is not a regular file (a FIFO, a device) is drift, and it is not read; so is a unit file or a list of the repository that is missing or a link that leads nowhere. The test hooks that its header lists, and `host-units.sh`'s, are named in a note when they are set (also one that a `BASH_ENV` file sets without `export`, and a run with `BASH_ENV` set says so), and one whose value the check cannot use (a time that is not a number of seconds, a pattern that does not compile or that matches its own text) stops it with a DRIFT line. Bash options of the environment that change how it runs (from `SHELLOPTS` or `BASHOPTS`: `noglob`, `errexit`, `keyword` and others) are turned off at its start, and a note names `SHELLOPTS` or `BASHOPTS` when the environment set them; `noexec` and `onecmd` cannot be turned off from inside, as its header says; `history` is turned off too, so that no `HISTFILE` gets the check's lines. No `GIT_*` variable of the caller's reaches its git commands, and a git command that does not end in time is named, with the limit, in a DRIFT line. A file of the service's checkout that cannot be read, a `.gitattributes` value that is not UTF-8, a unit or drop-in line that ends with a backslash (systemd joins such lines; the check does not, and `scripts/test.sh` refuses such a line) and an `ExecStart` that cannot be split into words are each a DRIFT line, not a traceback. It reads a unit's lines as systemd does: only a space, a tab, a carriage return and a line feed are blanks, and a unit is split at its line ends only; a value is compared as systemd shows it: a boolean in any of systemd's spellings (`true`, `on`, `1`, any case) as `yes` or `no`, a mode in octal, a limit's `soft:hard` pair, a size's `K`, `M`, `G`, a span's units, and a command's `@` prefix and program; `Environment=` is read from systemd's bus with `busctl`, item by item, since `systemctl show` prints an item with a blank as `[unprintable]`, and a repository line it cannot split, or a loaded `Environment` it cannot read, is a DRIFT line, not a traceback; a specifier or a C escape in a value, or `$VAR` in a command, is taken as written, a limit its header names; a byte order mark at the start of a line is skipped once, as systemd skips it; an empty assignment of a list (`ExecStart=`, `Environment=`) in a unit or drop-in of the repository empties the list before it, as systemd does; a drop-in of the repository for `strata-q3.service` or `zfs-arc-max.service` that sets what the rest of the check reads from the unit file alone (`ExecStart=`, and the service's `ExecStartPre=` and process settings) is drift, with the setting named; a NUL byte, where systemd ends a line, is drift, and the live config and the service's checkout are found also when blanks stand around the key. A live config with an `api_key` beside a missing or unreadable snapshot gives the snapshot's DRIFT line alone. From another checkout or worktree it passes only at the commit of the service's checkout, unless `--candidate` says that the tree is a commit to be deployed. Before, a replaced engine that still ran, an engine with other arguments or environment, a unit setting loaded from elsewhere and an edited preflight in the live checkout all gave `no drift`. It prints the names of environment variables, never their values, and never the service's command line. Since it reports uncommitted changes as drift, `README.md` and `docs/runbooks/change-config.md` now say to run it after a commit, not before.

### Changed

- The stub harnesses that start fake engines run in CI, and on this machine only with `scripts/test.sh --harnesses` while the service is stopped ([decision 0006](docs/decisions/0006-harnesses-in-ci-checks-by-hand.md)); CI's job may take 30 minutes, not 10, and decision 0003 says that each push to `main`, not each commit, gets a run. Their fake engines have the command line that the preflight takes for a second engine, so while `scripts/test.sh` ran them here, no start of `strata-q3` could succeed. The unit tests of commit e5d7908 took 585.9 s here, close to the 600 s that `scripts/deploy.sh` gave a check (`results/test-sh-20261020.txt`). `tests/harness_run.py` itself refuses to start such a harness unless it was asked for, and where systemd does not run unless `STRATA_TEST_NO_SERVICE=1` says that no service runs on the host; where the kernel has the NVIDIA driver loaded, as this machine's does (a container on it sees that too), the flag is not taken. The harness's file decides whether it is one: any that names the engine's directory, whatever its name, and every other `tests/*_stubs.sh` but `run_robustness_stubs.sh`, by its own name or that of the file a link leads to, in any case of letters; no argument of a test turns the gate off. CI sets the variable and installs gcc, libc6-dev, procps, iproute2, curl and shellcheck.
- `scripts/deploy.sh` leaves commits that change the checks to a person: `scripts/test.sh`, `scripts/host-units.sh`, `scripts/deploy.sh` itself, `tests/harness_run.py`, `.github/` and any `.gitattributes`, as it did for `scripts/check-drift.sh` (decision 0006). Before, such a commit was checked by the scripts it changed, and a commit that changed `deploy.sh` was deployed by the old one without a person reading it; its new `deploy.sh` then decided on the next commits. It gives each check 1800 s instead of 600 s: without the harnesses, `scripts/test.sh` takes about 22 minutes here (1303 s: `results/test-sh-20261027.txt`). It runs the new commit's `scripts/check-drift.sh` with `--candidate`, and runs both checks with nothing of its environment but `PATH`, `HOME`, the locale, `USER`, `LOGNAME`, `XDG_RUNTIME_DIR` and `TERM`, so a caller's test hooks, `BASH_ENV` or `PYTHONPATH` do not reach them. While a check runs, what the preflight refuses a start for (a process with its engine pattern, a listener on :8080) fails the check, unless it is the service's own; when it has the checks' TMPDIR in its environment, it is the check's, also in a session or a scope of its own (`systemd-run --user --scope`), and it is killed at once; one that someone else started in the same login session is not, nor one whose environment cannot be read. A last look, with a scan that starts after the check has ended, comes after it. The watch's exit status says whether it found anything; a watch that does not finish, or that a check keeps stopped, fails the check. After each check and on an interrupt, the script kills what a check left behind: each process that names its temporary directory as a path of its own, and each one with the checks' TMPDIR in any cgroup, with its process group when it leads one; one of another user's is named, not killed. It looks once more 0.2 s after a pass that finds nothing, since a process in the middle of its exec, after its `setsid`, has a command line and an environment that read empty, and it goes on killing when the terminal has hung up and its notes cannot be written. A clean-up that does not finish, or whose 20 passes still find something, fails the check. A process that drops that TMPDIR, leaves the session and names nothing of the directory is not found: that takes intent, which code review has to catch. On an interrupt it first ends a running check and its watch, with SIGTERM and SIGCONT and, 15 s later, SIGKILL, so a check that stops its timeout or the watch no longer hangs the script; a check that its timeout has not ended 30 s past the limit is ended too. Ctrl-\ ends nothing. Once the outcome is known (bad usage, which still ends with exit 2; for a check that failed, once its reason is known; and once the last check has ended, also before the script has seen it end, whether it passed or failed: `check-drift.sh --candidate` in a dry run, the check after the fast-forward with `--apply`), an interrupt (Ctrl-C, SIGTERM or SIGHUP) no longer changes the message or the exit status: the watch ignores SIGHUP and acts on its first SIGTERM only, so neither ends it with another exit status. A signal in the moment between the end of the last check and the shell's reaping of it still counts as an interrupt of that check. While it waits for a check, a signal to the script's process group (a Ctrl-C, a terminal that hangs up, `kill -- -PGID`) takes effect at once and puts nothing on stderr but the script's message; a SIGTERM to the script alone takes effect at the end of the current wait: within 0.1 s while the last check runs, so that only a last check that ends within that 0.1 s is reported as it ended, and within a second while an earlier check runs. A signal to the process group while a command runs in the foreground outside those waits (git, curl, the sweep) can still make bash note on stderr that it ended that command. A check after the fast-forward that fails is reported as `deployed <commit>, but scripts/check-drift.sh after it failed: <reason>`; before, every such failure read as drift. A Ctrl-C while the script prints commit subjects, reads the CI runs or sweeps after a check no longer makes Python print a traceback: these three short Python programs start with SIGINT ignored, so that Python sets no handler of its own (before, a Ctrl-C in their first milliseconds could still print one). An interrupted fetch can make git say why it stopped. Only a fetch killed outright (15 s after its SIGTERM, or by the OOM killer) can leave `.git/refs/remotes/origin/main.lock`; the next run then refuses with git's message naming the file, which is removed by hand once no git runs in the checkout. The temporary directory is removed also after a signal right after it was made. The traps are set before the script reads its arguments, so a Ctrl-C there ends it as an interrupt (exit 1); a signal in its first moments, before `main` sets them, ends it as the signal does, with nothing made or locked yet. An exit status of 137 before the limit is reported as a kill (SIGKILL), for example by the OOM killer at the account's limit, not as a time-out. The checks run with `oom_score_adj` 1000 (`choom`), so at the account's memory limit (decision 0007) the OOM killer takes their processes first, and at nice 19, as the watch does; the watch reads the listeners through sock_diag, which costs less than reading `/proc/net/tcp`. The fast-forward runs in the foreground in a session of its own, so a Ctrl-C lets it finish, and the script then says whether the commit is deployed. Before, an interrupt during the fast-forward said `not deployed` when the commit could be in place, or stopped git halfway. `docs/runbooks/deploy.md` gives the steps by hand: the CI run of the exact commit, a reading of what changed in the checks, the watchdog stopped while a start could see half of the change, `scripts/host-units.sh apply`, a restart of `zfs-arc-max.service`, a restart when what runs differs from what the repository gives, and the rollback of a commit that was deployed by hand.
- `scripts/test.sh`:
  - fails when no test ran (every test was skipped, by itself or with its class or module; a test that skipped only a subtest ran), when a test does not finish (it ends the process) or expects to fail, or when a test is skipped for another reason than `harness:` without `--harnesses` or `machine:` with `--repo-only`. Python 3.10's unittest exits 0 when no test ran. It also fails on a `.py` file under `tests/` that is neither a test module it loads (`tests/test_*.py`) nor a helper of theirs, and on a test that never runs. It finds those in the source (a method defined twice in one class or one of its blocks, one bound to something else later in its class or overridden by its TestCase, one in a class that is not a TestCase the runner loads nor a base of one, a generator, an async generator, an `async` one in a plain TestCase, also behind a `functools.wraps` decorator, and classes under `match`), and while the tests run, by the code that runs (cProfile): a loaded test that never starts (its class overrides `run()`), one whose function body never runs (a decorator returned without calling it) and one that returns something (a coroutine) fail. What the profiler sees run counts as run, so a test behind a decorator without `functools.wraps`, and a function outside a class named `test…`, pass when their code runs; such a function whose code never runs fails, unless code that may run reads it as a global (Python's `symtable`): a function whose code ran, a loaded test's function (also a skipped one), one that a loaded test holds, and in turn what those read (also a method of the module that those read as `self.NAME`, of their own class or a class related to it, or as `CLASS.NAME`). A module that skips itself at its import has none of its tests or functions checked, and a test that turns the profiler off is not checked. A file that is not a regular file (a FIFO) is reported and never opened.
  - compiles the Python instead of parsing it, so a misplaced `from __future__` fails now, and fails on a directory it cannot read, and on a shell script or a Python program anywhere in the repository but `results/` and dot directories that its steps do not read (by the interpreter its `#!` line names, also with options or through `env`; `*.bash` too).
  - compiles the Python inside the shell scripts. It reads a script as the shell does to find the commands it runs, and its header lists the forms it reads and the ones it refuses ("cannot read"), which fail the run. It reads heredocs, `python3 -c`, here-strings, command and process substitutions, subshells, groups, arrays (an array runs nothing, as `as_user=(runuser -u "$u" --)`, but python's code in one is compiled), `case`, `time` and `coproc`; the script's functions at each call, with their arguments, `shift` and the call's input; the code of `bash -c` and `sh -c` with the words after it (`$0` to `$9`, `"$@"`), of `su`, `sudo -s`, `runuser`, `sg`, `flock -c`, `trap`, `watch`, `script -c` and `source /dev/stdin`; a file of the repository that the script sources by a literal path; files that the script writes, also in parts, and then runs; a variable that the script sets once, at its top level and unconditionally, to one word (`SUDO=sudo`), also in that code; python's program from a file of the repository on its standard input; and the programs that run a command after their own options (`env`, `nice`, `timeout`, `setsid`, `sudo`, `systemd-run`, `xargs`, `find -exec` and others). It refuses python, or a shell, that reads a program it cannot read: from a pipe or the terminal, a process substitution, a variable, a command substitution, a heredoc whose delimiter is not quoted, `eval`, an alias, or a file written from words it cannot read; and python whose standard input is a file that is neither one the script wrote nor one of the repository (`python3 < /etc/job.py`). A program in a file that python or a shell names and that the script did not write is not read (`python3 /etc/job.py`, `bash "$JOB"`, `bash < /etc/job.sh`); the repository's `.sh` and `.py` files are read on their own. In code that a word gives a shell, it refuses an expansion of the outer script that starts a command, unless the variable is set once as above; a variable named like `PY` is python whatever it is set to. Any other program is one it does not follow (`ssh`, `at`, `batch`, `docker`, a terminal ...), so it refuses a word given to such a program that names python (also in a command substitution; not a variable's name, as `$ipython_dir`), an expansion, in a word, an input or a file the script wrote, of a variable named for python (a part of its name starts with `py`: `PY`, `PYBIN`, `VENV_PY`; not `PYTHONPATH`), or that any assignment sets to such a word (`INTERP=$(command -v python3)`, `RUN="$VENV/bin/python3 -u"`, `local b=python3`, `: "${INTERP:=python3}"`; not `PORT=$(python3 -c ...)` nor `N=$(curl ... | timeout 5 python3 -c ...)`, where python is only the program of the substitution's commands: that is python's output), also in the code of a new shell that the script starts (`export INTERP; bash -c '... "$INTERP" ...'`), or an array that holds one (also one built with `+=`), and a standard input from the script that names python; a file the script wrote, only when the program may run it or send it on (`scp`, a program with a shell among its words); the programs that only print or match text (`echo`, `printf`, `logger`, `grep`, `hash` ...), the script's own functions, and the words of `for`, `case`, `[[ ]]`, `(( ))` and arrays are not checked. So a message that names python, given to such a program, fails the run (`mail -s "python3 failed"`, `journalctl -g python3`); the header names this as a limit.
