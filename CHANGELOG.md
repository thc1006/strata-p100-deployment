## 2026-10-30

### Added

- A rehearsal of the rebuild on this machine, while the service ran, in a bubblewrap sandbox with production read-only and no GPU device (records `results/rebuild-rehearsal-*-20261030.txt`). The rehearsal ran copies of its tools in `~/rebuild-rehearsal`, whose sha256 are in `results/rebuild-rehearsal-copies-20261030.txt`. ### Added

- The maintainer's account may use at most 6 GiB of RAM and no swap (`systemd/user-1003.slice.d/50-memory.conf`, installed by `scripts/install-system-files.sh`; [decision 0007](docs/decisions/0007-memory-limit-of-the-maintainers-account.md)). On 2026-10-21 at 03:10:38 a review job in that account built a test input that grew to 29 GiB, the kernel's OOM killer took the engine, the largest process, and the service was down for 11 minutes (`results/oom-incident-20261021.txt`). A job that passes the limit is now killed inside the account. `scripts/check-deployment.sh` reports when the limit is not in force, when locked memory is charged to the account, and when it cannot read either.
- `scripts/check-drift.sh` compares what runs with the repository, not only the files on disk. Its header lists each check. The main changes:
  - It hashes the files of the Strata tree and of the service's checkout as git stores them, with the commit's own git attributes, instead of asking `git status`, which can hide a file. It writes nothing in the repositories.
  - It checks that the service manager gives every service only the locale and a `PATH` that only root can change. It compares each drop-in in `systemd/<unit>.d/` with its installed copy, reads every drop-in directory that systemd reads for a unit, and checks that systemd has loaded the drop-ins and that their memory limits are in the unit's cgroup.
  - While `strata-q3` is active, it checks that server.py runs as its unit says (command line, program, directory, user, limits, file-system sandbox, environment); that it runs one engine (none when the model is unloaded on purpose) and no other engine runs; that the engine is the listed binary with the command line, directory and environment that server.py makes of the live config; and that the engine maps the listed CUDA libraries and no file outside the system's directories that the list does not name or that was replaced after the start. A config setting whose effect the check does not follow (`vision`, `replicas`, a backend other than CUDA and others) is drift, and the engine must then be compared by hand. It sends the config's key only to `127.0.0.1`, `::1` or `localhost`, and only when server.py or its child is the only listener on the port.
  - A file that the service read at its start (the live config, the listed files except the records of how the pack and the venv were made, the server code, the venv, the installed unit) and that changed after the start is drift ("restart pending"). A file that the engine maps, whose inode alone changed and whose content is still the list's, gives a note instead. It checks the venv without running anything from it, against `config/strata-venv.txt`. A module or `.pth` file that Python would load and that neither the commit nor the list has is drift, and so is cached bytecode that Python would run instead of its source when it is not what that source compiles to.
  - Input it cannot read or parse (a missing file, a FIFO, a unit line it cannot split) is a DRIFT line, not a pass or a traceback. It names the caller's test hooks and `BASH_ENV` in a note, turns off the shell options that would change how it runs (all but `noexec` and `onecmd`, as its header says), and passes none of the caller's `GIT_*` variables to git.
  - From another checkout or worktree it passes only at the commit of the service's checkout, unless `--candidate` says that the tree is a commit to be deployed.

  Before, a replaced engine that still ran, an engine with other arguments or environment, a unit setting loaded from elsewhere and an edited preflight in the live checkout all gave `no drift`. It prints the names of environment variables, never their values, and never the service's command line. Since uncommitted changes are drift, `README.md` and `docs/runbooks/change-config.md` now say to run it after a commit.
- `config/deployed-artifacts.sha256` lists the files that the engine and server.py read and that it did not list: the IQ3_S pack's weights, tokenizer and chat template, the engine's build record, the MTP head's text file, the CUDA libraries and the venv's `pyvenv.cfg`. Under a heading of their own, it lists the records of how the pack and the venv were made, which neither reads. Decision 0004 said that the list held IQ3_S's pack; it held only the pack's `index.txt`. Files over 1 GiB are hashed only with `--full`, which took 684 s on 2026-10-27 (`results/check-drift-full-20261027.txt`); the MTP files are under 1 GiB, so every run hashes them. `config/strata-venv.txt` lists the venv's packages, each with the sha256 of its `RECORD`.
- `tests/test_start_path.py` runs the scripts of a service start, unchanged, against stubs: the preflight with the repository's `tools/configure_strata_q3.py` and `config/profile.conf` (on this machine only, since the preflight checks `/dev/nvidia3` itself), `scripts/strata-wait-ready.sh`, and the watchdog with `--dry-run`. Before, only `bash -n` read them, and bash 5.1's `bash -n` does not parse the body of `$( )`. It tests the preflight's memory gate, the watchdog's restart limits, cool-down and counters, and wait-ready's 30-minute limit. The tests that replace `/run` or `/proc/uptime` run in a user and mount namespace of their own (`unshare -Urm`) and are skipped (`machine:`) where one cannot be made. Not tested: that a run without `--dry-run` writes and removes the counter files.
- `results/ab2-iq3s-robust-robustness.log`, the log of decision 0004's robustness run on IQ3_S (`ab2-iq3s-robust`), with the host name written `<host>`. The run's other files were committed on 2026-10-20 without it.

### Changed

- The stub harnesses that start fake engines run in CI, and on this machine only with `scripts/test.sh --harnesses` while the service is stopped ([decision 0006](docs/decisions/0006-harnesses-in-ci-checks-by-hand.md)). Their fake engines have the command line that the preflight takes for a second engine, so while `scripts/test.sh` ran them here, no start of `strata-q3` could succeed. The unit tests of commit e5d7908 took 585.9 s here, close to the 600 s that `scripts/deploy.sh` gave a check (`results/test-sh-20261020.txt`). `tests/harness_run.py` refuses to start such a harness unless it was asked for. Where systemd does not run, it also needs `STRATA_TEST_NO_SERVICE=1`, which says that no service runs on the host; where the kernel has the NVIDIA driver loaded, as this machine's does (a container on it sees that too), the flag is not taken. The harness's file decides whether it is one, not an argument of the test (the rules are in the header of `tests/harness_run.py`). CI's job may take 30 minutes, not 10; it sets the variable and installs gcc, libc6-dev, procps, iproute2, curl and shellcheck. Decision 0003 now says that each push to `main`, not each commit, gets a run.
- `scripts/deploy.sh` leaves to a person the commits that change the checks: `scripts/test.sh`, `scripts/host-units.sh`, `scripts/deploy.sh` itself, `tests/harness_run.py`, `.github/` and any `.gitattributes`, as it did for `scripts/check-drift.sh` (decision 0006). Before, such a commit was checked by the scripts it changed, and a commit that changed `deploy.sh` was deployed by the old one without a person reading it. The other changes (decision 0006 gives more):
  - Each check gets 1800 s instead of 600 s: without the harnesses, `scripts/test.sh` takes about 22 minutes here (1303 s: `results/test-sh-20261027.txt`).
  - It runs the new commit's `scripts/check-drift.sh` with `--candidate`. Both checks get only `PATH`, `HOME`, the locale, `USER`, `LOGNAME`, `XDG_RUNTIME_DIR` and `TERM` of its environment, so a caller's test hooks, `BASH_ENV` or `PYTHONPATH` do not reach them.
  - While a check runs, what the preflight refuses a start for (a process with the engine pattern, a listener on :8080) fails the check unless it is the service's own; one with the checks' TMPDIR in its environment counts as the check's, also in a session or scope of its own, and is killed at once. After each check and on an interrupt, the script kills what the check left behind (a process of another user's is named, not killed). A process that drops the check's TMPDIR, leaves the session and names nothing of its directory is not found: that takes intent, which code review has to catch.
  - The checks run at nice 19, and with `oom_score_adj` 1000 (`choom`), so that at the account's memory limit (decision 0007) the OOM killer takes their processes first.
  - A check that stops its timeout or the watch no longer hangs the script. Once the outcome is known (decision 0006 says when, and gives the one exception), an interrupt no longer changes the message or the exit status. The fast-forward runs in the foreground in a session of its own, so a Ctrl-C lets it finish, and the script then says whether the commit is deployed. Before, an interrupt during the fast-forward said `not deployed` when the commit could be in place, or stopped git halfway.
  - A failed check after the fast-forward is reported as `deployed <commit>, but scripts/check-drift.sh after it failed: <reason>`; before, every such failure read as drift. An exit status of 137 before the limit is reported as a kill (SIGKILL), for example by the OOM killer, not as a time-out.
  - A Ctrl-C while it prints commit subjects, reads the CI runs or sweeps no longer prints a Python traceback. The traps are set before it reads its arguments, and the temporary directory is removed also after a signal right after it was made.
  - Only a fetch killed outright (15 s after its SIGTERM, or by the OOM killer) can leave `.git/refs/remotes/origin/main.lock`. The next run then refuses with git's message naming the file; remove it by hand once no git runs in the checkout.

  `docs/runbooks/deploy.md` gives the steps by hand: the CI run of the exact commit, a reading of what changed in the checks, the watchdog stopped while a start could see half of the change, `scripts/host-units.sh apply`, a restart of `zfs-arc-max.service`, a restart when what runs differs from what the repository gives, and the rollback of a commit that was deployed by hand.
- `scripts/test.sh` (its header gives the unit tests' rules and limits, and each step's comments give its own):
  - fails when no test ran (Python 3.10's unittest exits 0 then), when a test does not finish, expects to fail or returns something (a coroutine), when a test is skipped for another reason than `harness:` without `--harnesses` or `machine:` with `--repo-only`, and when a test never runs. It finds a test that never runs in the source (a method defined twice, a test in a class that is neither a TestCase the runner loads nor a base of one, a generator, and other forms) and, while the tests run, with cProfile: a test whose body never runs fails. It also fails on a `.py` file under `tests/` that is neither a test module it loads (`tests/test_*.py`) nor a helper of theirs.
  - compiles the Python instead of parsing it, so a misplaced `from __future__` fails now. It fails on a directory it cannot read, and on a shell script or Python program anywhere in the repository but `results/` and dot directories that its steps do not read (found by the interpreter of its `#!` line too).
  - compiles the Python inside the shell scripts, in the forms that the comments of its Python step list. A program it cannot read, such as python that reads its program from a pipe or a variable, fails the run ("cannot read"); a program in a file that the script did not write (`python3 /etc/job.py`) is not read. A limit: a message that names python, given to a program it does not follow, fails too (`mail -s "python3 failed"`). Before, it parsed only the `.py` files under `bench/`, `tools/` and `tests/` (`ast.parse`), and did not read the Python inside the shell scripts.
  - runs shellcheck for errors. With `--repo-only`, and so in CI, shellcheck must be installed.
  - splits every Exec line of every unit and drop-in as systemd does, checks the programs it runs, and fails on a line it cannot read and on anything else in `systemd/`. Before, it skipped lines in some forms and still counted them as checked. `systemd-analyze verify` reads the tested tree's units and the distribution's, not this machine's `/etc` and `/run`; the distribution's units differ between this machine and CI's container, so a unit can pass here and fail in CI. The comments of the step give the rest.
- `scripts/strata-health.sh --dry-run` says what it would set and clear (`strata-health: (dry run) would set engine_failures to 3`, `strata-health: (dry run) would clear http_failures engine_failures`), so a dry run of a healthy service is no longer silent. Before, no test could see whether the watchdog counts each failed check and each attempt to start a failed service, or whether it clears its counts: a count left behind would add misses that were not in a row toward a restart, and attempts left behind would keep a failed service's cool-down at 8 hours. A run without `--dry-run` writes and removes the counter files as before. The maintainer approved both changes on 2026-10-25.

### Fixed

- `scripts/strata-preflight.sh` runs its Python with `-I`. Before, a `.pth` file in the service user's site-packages, or a `sitecustomize` on `PYTHONPATH`, ran in the service's start path.
- `scripts/strata-wait-ready.sh` and the watchdog run curl with `-q`, so that no `.curlrc` changes their requests. Before, an `output` line in a `.curlrc` (the service user's for wait-ready, root's for the watchdog) hid every answer: wait-ready waited until it gave up, and the watchdog would have asked server.py to load a model that was unloaded on purpose.
- `scripts/check-deployment.sh` put the API key (`STRATA_KEY`) on curl's command line, which every account on the machine can read in `/proc`. It now writes the key to a 0600 header file in a directory of its own (`-H @file`), and does not send a key that holds a control character. It also runs curl with `-q`: before, an `output` line in `~/.curlrc` hid the server's answers, and the check said `no problems found` without having read `/health`. And it runs curl with `--noproxy '*'`: before, curl sent each request, with the key, to a proxy that `http_proxy`, `all_proxy` or `ALL_PROXY` named, also for `127.0.0.1`. `tests/test_check_deployment.py` tests all three.
- `scripts/check-deployment.sh` lists the last 12 lines of the last 2 hours that name the watchdog, the preflight, wait-ready, a start or a failure. systemd's Starting and Finished lines of each health check name the watchdog's script too, and with a check every 2 minutes they filled the 12 lines and left out the events. Those lines are left out now, and `tests/test_check_deployment.py` tests it; `docs/runbooks/operations.md` says what the list holds.
- `scripts/strata-wait-ready.sh` and the watchdog sent their requests to a proxy that `http_proxy`, `all_proxy` or `ALL_PROXY` named, also for `127.0.0.1`, and took its answers for the server's. Under systemd they get no such variable, but a root run with the caller's environment (`sudo -E scripts/strata-health.sh --dry-run`) sent the live config's key through that proxy, and so would a dry run without root. Both run curl with `--noproxy '*'` now, and `tests/test_start_path.py` tests it.
- `scripts/strata-health.sh --dry-run` made `/run/strata-q3-health`, changed its mode and wrote its temporary files (the key's header) there, and without root it could not write those files at all. A dry run now changes nothing there: its temporary files go to a directory of its own.
- `tests/harness_run.py`: a harness test stopped by `deploy.sh`'s time limit, a Ctrl-C or a SIGTERM left the harness and its fake engines running, since they run in a session of their own. Now the harness's process group gets SIGTERM, and SIGKILL 60 s later; then every process still in the harness's session, or whose command line names its directory, is killed and reported, also after a normal end (under `deploy.sh`'s limit, `scripts/test.sh` ends at the SIGTERM and `deploy.sh` kills them). Its header gives the details. A driver inside another harness's sandbox no longer counts as a running experiment, and every `bench/*.sh` now does, also one started by a relative path or through a link; a job queued for `strata-q3` counts as well. `tests/ab_engine_stubs.sh` and `tests/ab_model_run_stubs.sh` name their sandbox in the command lines they start with `setsid`, so that the clean-up finds them.
- `scripts/host-units.sh` neither checked nor applied a last line of `config/host-units.conf` without a newline, so a unit there in the wrong state passed `check`, and `apply` left it alone; such a line is read now. A list that is a FIFO hung both modes, and a list that is missing or cannot be read gave exit 1 with a message on standard error only; each is now a DRIFT line on standard output. The commands of its loop got the rest of the list as their standard input, so one that reads it, as a `sudo` that logs its input does, took the remaining lines; the list is read on a descriptor of its own now.
- `scripts/check-drift.sh` reported a file it could not read, or one that was missing, as a difference: a repository copy or an installed file, the live config, the deployed snapshot or `config/strata-iq3_xxs.setup.json`. It exited 1 with no DRIFT line when `scripts/host-units.sh` was missing or failed without one. Each is now a DRIFT line that names the file.
- `scripts/check-drift.sh` and `scripts/host-units.sh` ran a shell function that the environment exported (or that a `BASH_ENV` file made) in place of the command of its name: an exported `cmp` that returns 0 hid every difference, and an exported `systemctl` that answers `masked` passed every unit. Run by their path, as `scripts/deploy.sh` runs `check-drift.sh`, both are now under `bash -p`, which takes no function, shell option or `BASH_ENV` file from the environment, and `check-drift.sh` runs `host-units.sh` under `bash -p` too. Run as `bash <script>`, they remove every function, turn off the options that change what they do, and stop with a DRIFT line when a function is left. Only exported functions named both `compgen` and `declare` still go unseen, a limit their headers name.
- `scripts/check-drift.sh` took the ARC values that `zfs-arc-max.service` writes from every line of the unit, comments too, so a comment that held an `echo N > /sys/module/zfs/parameters/…` command made every run report drift, and every later deploy was refused. It now reads them from the unit's `ExecStart` lines only; two values for one parameter are drift, and a parameter that no line writes is named.
- `scripts/strata-preflight.sh` took the ARC cap it compares with `zfs_arc_max` from every line of the installed `zfs-arc-max.service`, so such a comment gave a false note, or hid a missing one. It takes it from the unit's `ExecStart` lines only now. It is a note only, not a refusal. The maintainer approved the change on 2026-10-27.
- `scripts/check-drift.sh` and `scripts/host-units.sh`, run by a relative path with `CDPATH` in the environment, read none of their files. They now ignore `CDPATH`.
- `tests/test_host_units.py` ran `scripts/host-units.sh check` with the system's `PATH` after its stand-in of `systemctl`, so a regression of the script into its `apply` branch would have run the real `sudo`, and through it the real `systemctl`, as root. Both modes now run with stand-ins of both on a `PATH` of a few programs, under `setpriv --no-new-privs`, without a D-Bus address and with an empty `XDG_RUNTIME_DIR`; in `check`, the stand-in `systemctl` may get no call but `is-enabled`, `is-active` and `get-default`.
- `scripts/host-units.sh` took an unreadable `is-active`, and `reloading` or `deactivating`, for a unit that does not run; now only `inactive` and `failed` count. Without `XDG_RUNTIME_DIR`, as in a cron job, it reads the user units through the account's runtime directory when one exists; otherwise they are reported unreadable, as before.
- Decision 0004's step 6 named the robustness run's monitor by the tag planned for it, `ab-iq3s-robust`, which no run had; an amendment names the two files the runs made (`ab2-` and `ab3-iq3s-robust-robust-monitor-all.json`).
- Decision 0004 cited `results/iq3s-memory-budget-20261019.txt` for RAM figures and routing shares that came from a computation of 2026-10-18, which it said was not kept, and some of its figures were wrong. `results/q4-budget-20261022.txt` holds that computation, run again on its saved inputs with the same output, and the record cites it.
