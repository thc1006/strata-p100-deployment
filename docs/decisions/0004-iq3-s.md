# Serve GSQ-RCO IQ3_S instead of IQ3_XXS, with 6 GiB RAM floors and a 2 GiB ZFS ARC

## Context and Problem Statement

On 2026-10-18 the maintainer asked whether a 4-bit quantization of the model fits this machine, and to use its RAM
to the limit while keeping 6 GiB free: the box serves only this model. The service then ran ISTA-DASLab's GSQ-RCO
IQ3_XXS (see [the deployment record](../deployment-record.md)).

Where each candidate would live (`results/iq3s-memory-budget-20261018.txt`, computed from the GGUF tensor headers;
for IQ3_XXS the per-card sums equal the engine log of the 2026-10-18 02:26 start, 9.41 / 9.88 / 11.43 / 9.25 GiB):

|---|---:|---:|---:|
| GSQ-RCO IQ3_XXS (deployed) | 75.8 GB | 39.97 GiB | 26.82 GiB, IQ4_NL |

## Considered Options

1. Keep IQ3_XXS.
2. GSQ-RCO IQ3_S.
3. Unsloth UD-IQ4_XS.
4. A 4-bit file: bartowski Q4_0, IQ4_XS or Q4_K_M, or Unsloth UD-Q4_K_XL.

## Pros and Cons of the Options

- **4-bit files do not fit.** The numbers below assume a 6 GiB floor, the ARC at 2 GiB, 32K context and a 1024 MiB
  reserve; even then, the experts that VRAM cannot hold do not fit in the RAM that is left.

  | File | RAM short |
  |---|---:|
  | bartowski Q4_0 | 1.5 GiB |
  | Unsloth UD-Q4_K_XL | 11.2 GiB |

  - bartowski IQ4_XS would leave 1.2 GiB, with 12% of the routing computed on the CPU.
  - bartowski Q4_K_M's Q5_0 down projections run only on the FP16 prompt path.
- **UD-IQ4_XS fits only without longer context.**
  - With the ARC at 2 GiB, 5.3 GiB is left above the floor, and 8.8% of the routing is computed on the CPU (42 of 480
    expert products per token).
  - Its routed experts are IQ3_S gate/up with IQ4_NL down; only its dense side is Q8_0. Its mean KL against Q8_0 is
    lower than IQ3_S's (0.101 against 0.144), but its perplexity is higher (4.120 against 4.097).
  - It needs `--compat-bf16`, which on a Strix Halo put perplexity 6-9% above llama.cpp on the same file
    (UNSLOTH_Q4.md).
- **IQ3_S fits almost entirely in VRAM.** It has 6.87 GiB more experts than IQ3_XXS.
  - At the 1536 MiB reserve with cuts 13 / 25 / 38, the four expert caches hold 98.97% of the expert profile's
    routing, so 4.9 of 480 products per token are computed on the CPU. At the deployed cuts 13 / 26 / 38 they hold
    98.67%.
  - Its formats (IQ2_S, IQ3_XXS, IQ3_S and IQ4_XS gate/up; IQ4_NL and Q2_0 down) have sm_60 kernels in the deployed
    engine.
- **The VRAM reserve stays at 1536 MiB.**
  - With IQ3_XXS the cache was never full, so the reserve never bound.
  - With IQ3_S the cache fills each card down to the reserve. During the deployed robustness run each card's use grew
    by up to 490 MiB after the first sample (`results/deployed-robust-monitor-all.json` against its first CSV row).
  - A 1024 MiB reserve would therefore leave about 0.3-0.5 GiB free, the range where upstream #2065 reports a hang.

## More Information

**Criteria and protocol, amended on 2026-10-18 at 23:36 and on 2026-10-19 at 01:15, after three adversarial reviews
and before any IQ3_S measurement.** The first version (commit d95cd7a, 2026-10-18 22:36) measured the baseline on the
engine that had run for 20 hours, in the order ABAB, judged the speed on the means only, and ran the quality subset in
the service's default mode with one sample per item. The third review found that the tools would have failed a stable
IQ3_S on lines that are not faults: a request that waits 90 s for a slot (the Poisson phase overloads the 4 slots on
purpose, and earlier perf runs logged such waits), another client's request, an interrupted run. It also found that
the 300 s were counted from the engine's start, inside the 7-9 minute load, and that the values step 1 deploys were
compared between the runs but never checked. Each finding is now a test in `tests/test_ab_model_summary.py` or
`tests/ab_model_run_stubs.sh`. IQ3_S is kept when all three criteria hold.

**Protocol for speed and stability** (`bench/ab_model_run.sh` around the standard perf set, `bench/run_profile.sh`;
judged by `bench/ab_model_summary.py`, whose exit status is the verdict):
1. The host changes below and the 6 GiB floors are deployed first, so that every run has them. The summary checks
   each run against this repository: the ARC cap of `systemd/zfs-arc-max.service`, both floors and the model's layer
   cuts in `tools/configure_strata_q3.py`, the PLE file as shard 2 of the loaded model, `config/profile.conf` naming
   that model, and the host units as `config/host-units.conf` sets them.
2. Four runs in the order ABBA, A the baseline: `ab-iq3xxs-1`, `ab-iq3s-1`, `ab-iq3s-2`, `ab-iq3xxs-2`. The service is restarted
   before every run, so each run has an engine of its own. A run starts 300 s or more after the service became ready
   (the model loaded) and when no request is in flight.
3. serve_load's prompts are the same in every run (nonce `ab-0004`), so each run decodes the same text. With the
   default nonce (the clock) two runs of one configuration differed by up to 4.8% on 1 client
   (`results/v441-1-serve_load.json` against `results/v441-2-serve_load.json`) and by 0.5% or less on 2 and 4 clients:
   the 1-client rate follows how many drafts the decoded text accepts.
4. The runs differ in the model only: the summary refuses runs whose other engine arguments, environment, engine,
   server.py, serve_load.py, config without the model's fields, shared settings, service code or perf set (sha256 of
   their files; a commit of results between runs changes neither) differ, or whose model name is not the model the
   engine loaded.
5. The run that was measured before these changes (`iq3xxs-1`'s arm record of 2026-10-18 22:31, with an 8 GiB ARC
   and 8 GiB floors) is kept as a raw result and is not part of the A/B.

**Criteria:**
1. **Stable.**
   - In each IQ3_S run: the same engine at the end; no error line in the engine log, no fault line in the service
     journal (systemd's own lines included), no NVIDIA Xid and no OOM kill of the service or of the whole host; all
     98 requests completed, none cancelled; no failed request.
   - A request that waits for a slot is queueing, not a fault; a slot freed as leaked is a fault. Lost or cancelled
     requests count only when the perf set ran to its end and no other client was active.
   - A baseline run that is not clean makes the A/B impossible to judge, not failed. So does a run with other
     traffic (more than 98 requests, a refused request, a request still running at the end), a run that did not
     finish (interrupted, a client error, a record missing), or a kernel problem that names no process of the
     service: that run is measured again.
   - During the robustness run on IQ3_S, every card keeps at least 700 MiB of VRAM free, and MemAvailable stays at or
     above the 6 GiB floor.
2. **Not much slower.**
   - The two baseline runs must agree within 5% on every metric below; otherwise the A/B cannot be judged.
   - On the total decode rate with 1, 2 and 4 clients and on the 4.4K and 32K prompt rates, the mean of the IQ3_S runs
     and each IQ3_S run may be at most 10% below the baseline's mean.
   - On the time to first token of a 16K prompt that joins three decoders, they may be at most 15% above it.
   - Faster is never a failure.
3. **Not worse in quality**, measured in the strongest mode (the template's xhigh, no thinking budget, the rest of the
   32K context, the model card's sampling) with `driver2.py`, the same harness as the comparison with the remote
   service.
   - The benchmarks, the samples per item and the non-inferiority margin come from a power analysis that is recorded
     here before the quality runs start.
   - Scoring: OpenAI simple-evals' multiple-choice extraction (vendored at commit 652c89d0ca9d), MathArena's boxed
     answer, the official IFBench and LiveCodeBench graders. Each benchmark gets the paired difference with its 95%
     interval, a sign-flip permutation test and McNemar's test; Holm's correction applies across the benchmarks.

If only the speed criterion fails, the maintainer decides between quality and speed with the numbers in hand.

  `results/host-units-before-20261018.txt`).
- The ARC cap went from 8 to 2 GiB (`systemd/zfs-arc-max.service`).
